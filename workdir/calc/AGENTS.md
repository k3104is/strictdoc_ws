# プロジェクト

このリポジトリで作業する際は、既存のアーキテクチャ、ディレクトリ構成、命名規則、コーディングスタイルを尊重すること。

プロジェクト全体の概要、ビルド方法、利用方法については `README.md` を参照すること。

# リポジトリ構成

基本的なディレクトリ構成:

```text
src/        製品コード
include/    公開インターフェース
test/       テストコード
docs/       ドキュメント・要求仕様
scripts/    開発支援スクリプト
build/      ビルド生成物
```

`build/` などの生成ディレクトリは手動で編集しないこと。

新しいディレクトリを追加する場合は、既存構成との整合性を確認すること。

# 作業の基本方針

* 必要最小限の変更を行うこと。
* タスクに関係のないファイルを変更しないこと。
* 既存の設計、命名規則、コーディングスタイルに従うこと。
* 明示的な指示がない限り、既存の動作を変更しないこと。
* 明示的な指示がない限り、公開インターフェースを変更しないこと。
* 生成ファイルを直接編集しないこと。
* 不要なリファクタリングを同時に行わないこと。
* 新しい依存関係の追加は必要最小限とすること。
* テストを通すためだけの変更を行わないこと。

# 変更前の確認

変更前に、必要に応じて以下を確認すること。

1. 関連する既存コード
2. 関連するテスト
3. 関連する要求仕様
4. 関連する設計資料
5. `README.md`
6. ビルド設定

既存実装に同等の処理やパターンが存在する場合は、それを優先して参考にすること。

# ビルド

標準ビルド:

```bash
cmake -S . -B build -G Ninja
cmake --build build
```

ビルド方法がプロジェクト固有の場合は `README.md` の記載を優先すること。

既存のビルドディレクトリが利用できる場合は、不必要に削除しないこと。

# テスト

コードを変更した場合は、変更内容に関連するテストを実行すること。

標準テスト:

```bash
ctest --test-dir build --output-on-failure
```

可能であれば、作業完了前に全テストを実行すること。

新しい動作を追加した場合は、必要に応じてテストを追加または更新すること。

以下は禁止する。

* テストを通すためだけに既存テストを削除する
* テスト条件を不必要に弱める
* 失敗しているテストを理由なく無効化する

# エラー修正

ビルドまたはテストが失敗した場合:

1. エラーメッセージを確認する
2. 原因を特定する
3. 原因に対して最小限の修正を行う
4. 再度ビルドする
5. 再度テストする

エラーを隠すだけの変更や暫定回避は避けること。

# コード品質

* コードから明らかな内容を説明するだけのコメントは追加しないこと。
* コメントは主に「何をしているか」ではなく「なぜそうしているか」を説明すること。
* 重複コードを不必要に増やさないこと。
* 不必要に複雑な抽象化を追加しないこと。
* 将来必要になるかもしれないという理由だけで機能を追加しないこと。
* 既存コードの設計思想を優先すること。

# ドキュメント

以下を変更した場合は、関連ドキュメントの更新が必要か確認すること。

* 公開インターフェース
* 外部仕様
* ビルド方法
* 実行方法
* 設定方法
* ディレクトリ構成
* 依存関係
* 要求仕様
* アーキテクチャ

# Git

作業開始時および作業完了前に必要に応じて確認すること。

```bash
git status
git diff
```

以下は明示的に依頼された場合のみ実行すること。

* `git commit`
* `git push`
* `git rebase`
* `git reset --hard`
* 既存コミットの変更

他の開発者による未コミットの変更を削除または上書きしないこと。

# 依存関係

新しいライブラリやツールを追加する前に以下を確認すること。

1. 標準ライブラリで実現できないか
2. 既存の依存ライブラリで実現できないか
3. 新しい依存関係が本当に必要か

新しい依存関係を追加する場合は、その理由が明確になるようにすること。

# Definition of Done

作業完了前に以下を確認すること。

1. 要求された変更が実装されている
2. ビルドが成功する
3. 関連するテストが成功する
4. 必要なテストが追加または更新されている
5. 必要なドキュメントが更新されている
6. `git diff` を確認している
7. `git status` を確認している
8. タスクと無関係なファイルを変更していない
9. デバッグコードや一時ファイルが残っていない

## StrictDoc

このプロジェクトでは要求仕様をStrictDocで管理する。

コードの動作・外部仕様・機能を追加または変更する場合は、
対応する要求仕様の追加・更新が必要か必ず確認すること。

必要な場合は、コード変更とあわせて `.sdoc` を更新すること。

- 既存のRequirement UIDを不用意に変更しないこと。
- 既存のトレーサビリティを維持すること。
- 新しい機能を追加する場合は、対応する要求仕様が存在するか確認すること。
- 対応する要求仕様が存在しない場合は、既存の構成・命名規則に従って追加すること。
- 要求仕様の意味を推測だけで変更しないこと。
- `.sdoc` を変更した場合はStrictDocで検証すること。

検証:

```bash
strictdoc export docs
```
