# プロジェクト

このリポジトリで作業する際は、既存のアーキテクチャ、ディレクトリ構成、命名規則、コーディングスタイルを尊重すること。

プロジェクト全体の概要、ビルド方法、利用方法については `README.md` を参照すること。

# リポジトリ構成

基本的なディレクトリ構成:

```text
src/        製品コード
include/    公開インターフェース
test/       テストコード
docs/       ドキュメント・要求仕様
scripts/    開発支援スクリプト
build/      ビルド生成物
```

`build/` などの生成ディレクトリは手動で編集しないこと。

新しいディレクトリを追加する場合は、既存構成との整合性を確認すること。

# 作業の基本方針

* 必要最小限の変更を行うこと。
* タスクに関係のないファイルを変更しないこと。
* 既存の設計、命名規則、コーディングスタイルに従うこと。
* 明示的な指示がない限り、既存の動作を変更しないこと。
* 明示的な指示がない限り、公開インターフェースを変更しないこと。
* 不要なリファクタリングを同時に行わないこと。

# 変更前の確認

変更前に、必要に応じて以下を確認すること。

1. 関連する既存コード
2. 関連するテスト
3. 関連する要求仕様
4. 関連する設計資料
5. `README.md`
6. ビルド設定

既存実装に同等の処理やパターンが存在する場合は、それを優先して参考にすること。

# ビルド

標準ビルド:

```bash
cmake -S . -B build -G Ninja
cmake --build build
```

ビルド方法がプロジェクト固有の場合は `README.md` の記載を優先すること。

既存のビルドディレクトリが利用できる場合は、不必要に削除しないこと。

# テスト

コードを変更した場合は、変更内容に関連するテストを実行すること。

標準テスト:

```bash
ctest --test-dir build --output-on-failure
```

可能であれば、作業完了前に全テストを実行すること。

新しい動作を追加した場合は、必要に応じてテストを追加または更新すること。

以下は禁止する。

* テストを通すためだけに既存テストを削除する
* テスト条件を不必要に弱める
* 失敗しているテストを理由なく無効化する

# エラー修正

ビルドまたはテストが失敗した場合:

1. エラーメッセージを確認する
2. 原因を特定する
3. 原因に対して最小限の修正を行う
4. 再度ビルドする
5. 再度テストする

エラーを隠すだけの変更や暫定回避は避けること。

# コード品質

* コードから明らかな内容を説明するだけのコメントは追加しないこと。
* コメントは主に「何をしているか」ではなく「なぜそうしているか」を説明すること。
* 重複コードを不必要に増やさないこと。
* 不必要に複雑な抽象化を追加しないこと。
* 将来必要になるかもしれないという理由だけで機能を追加しないこと。
* 既存コードの設計思想を優先すること。

# ドキュメント

以下を変更した場合は、関連ドキュメントの更新が必要か確認すること。

* 公開インターフェース
* 外部仕様
* ビルド方法
* 実行方法
* 設定方法
* ディレクトリ構成
* 依存関係
* 要求仕様
* アーキテクチャ

# Git

作業開始時および作業完了前に必要に応じて確認すること。

```bash
git status
git diff
```

以下は明示的に依頼された場合のみ実行すること。

* `git commit`
* `git push`
* `git rebase`
* `git reset --hard`
* 既存コミットの変更

他の開発者による未コミットの変更を削除または上書きしないこと。

# 依存関係

新しいライブラリやツールを追加する前に以下を確認すること。

1. 標準ライブラリで実現できないか
2. 既存の依存ライブラリで実現できないか
3. 新しい依存関係が本当に必要か

新しい依存関係を追加する場合は、その理由が明確になるようにすること。

# Definition of Done

作業完了前に以下を確認すること。

1. 要求された変更が実装されている
2. ビルドが成功する
3. 関連するテストが成功する
4. 必要なテストが追加または更新されている
5. 必要なドキュメントが更新されている
6. `git diff` を確認している
7. `git status` を確認している
8. タスクと無関係なファイルを変更していない
9. デバッグコードや一時ファイルが残っていない

* ビルドシステム: CMake

## StrictDoc

要求仕様は日本語で記載すること。利害関係者ニーズを除く各要求の `COMMENT` は「検証方法：」で始め、検証手段と合否基準を明記すること。利害関係者ニーズには検証方法を設定しないこと。ソフトウェア要求には、可能な限り自動テストまたは具体的なCLI試験を示すこと。

各要求には、次の要求レベルタグのうち1つだけを `TAGS` に設定すること。分類用のタグは追加してよい。

- `stakeholder-need`：利害関係者ニーズ
- `stakeholder-requirement`：利害関係者要求
- `system-requirement`：システム要求
- `software-requirement`：ソフトウェア要求

要求レベルは `TAGS` で判定し、UIDやタイトルに依存しないこと。

`Parent` 関係は次に限定すること。

- 最上位の利害関係者ニーズには設定しない
- 下位の利害関係者ニーズの親は、上位の利害関係者ニーズとする
- 利害関係者要求の親は、導出元となる利害関係者ニーズとする
- システム要求の親は利害関係者要求とする
- ソフトウェア要求の親はシステム要求とする
- 下位の利害関係者ニーズ、利害関係者要求、システム要求、ソフトウェア要求には1件以上設定する
- 要求レベルを飛び越えない

複数の上位要求から導出される場合は、複数の `Parent` を設定してよい。

### 利害関係者要求分析

利害関係者ニーズから利害関係者要求を作成、変更、分割、統合または廃止する場合は、次の順に分析すること。

1. **情報整理**：個別に収集された機能、期待成果、異常時の期待、制約などについて、出典、利害関係者、利用目的、運用場面、前提を整理する。
2. **正規化**：各ニーズから主体、目的、対象、条件、成果を抽出し、曖昧さ、重複、矛盾、欠落、粒度、解決策への過度な依存を確認する。
3. **ニーズの構造化**：利用目的を表す最上位ニーズと、その詳細となる機能、正常時・異常時の期待成果、制約などの下位ニーズへ分割・統合し、階層化する。階層はStrictDocのRequirementと `Parent` で表現する。
4. **要求への統合**：最上位ニーズだけでなく、その配下のニーズ情報全体を分析し、利害関係者、目的、適用範囲、優先順位、合意単位に基づいて利害関係者要求へ分割・統合する。同一の利用目的に属する情報は過度に細分化しない。
5. **要求案作成**：ニーズ階層から読み取れる目的と期待成果を、解決手段へ踏み込みすぎない明確で検証可能な要求として記載する。具体的なシステム動作、代替・例外フロー、エラー判定、応答方法は、後続のシステム要求分析で明確化する。
6. **影響分析**：UID、検証方法、下位要求、トレーサビリティ、既存仕様への影響を確認する。
7. **網羅性確認**：出典、最上位と下位のニーズ、構造化後の利害関係者要求、下位のシステム要求の対応と内容を確認する。
8. **レビュー・合意**：正確性、完全性、妥当性、優先順位をレビューし、合意後に確定する。

分析結果は `docs/requirements/stakeholder/利害関係者要求分析.md` に保存すること。確定したニーズと要求について、分析文書と `.sdoc` のUID、要求文、導出関係を一致させること。利害関係者要求の検証方法も一致させること。

分析前後の検討過程は分析文書に記録し、`.sdoc` には合意済みの利害関係者ニーズと構造化後の利害関係者要求だけを記載すること。未合意の案は `.sdoc` に反映しないこと。

既存UIDは原則として維持し、同じUIDへ異なる意味の要求を上書きしないこと。要求の意味や範囲が変わる場合は新しいUIDを設定し、参照先を更新すること。

### システム要求分析

システム要求を作成、変更または廃止する場合は、利害関係者要求を起点として次の順に分析すること。

1. **システムコンテキスト**：境界、外部アクター、外部システム、外部インタフェース、前提、運用環境、運用状態、制約を整理する。
2. **ユースケース抽出**：目的、アクター、関連要求を明記し、抜け漏れと重複を確認する。
3. **ユースケース図**：アクター、システム境界、ユースケース、関係をPlantUMLで記載する。
4. **シナリオ分析**：事前条件、トリガー、メイン・代替・例外フロー、事後条件を整理し、異常、操作不成立、外部環境の変化、状態遷移を考慮する。各フローの各ステップには、ユースケース内で一意かつ参照可能なIDを付与する。IDはメインフロー、代替フロー、例外フローを識別できる形式とし、分析文書内で一貫して使用する。ステップIDは、メインフローを `UC-01-MF-01`、代替フローを `UC-01-AF-01-01`、例外フローを `UC-01-EF-01-01` のように表記する。代替・例外フローについては、分岐元ステップを明記する。ユースケースごとに、各フロー、アクター、システム、および必要な外部システムの関係を示すPlantUMLアクティビティ図を作成する。
5. **要求導出**：シナリオ分析で定義したフローおよびステップIDを参照し、機能要求を導出する。機能要求に加え、性能、安全性、信頼性、セキュリティ、保守性、外部インタフェース、運用環境の観点から非機能要求と制約要求を検討する。アクティビティ図で不足する場合は、シーケンス図、状態遷移図・表、タイミングチャート、真理表を用いる。図はPlantUML、表はMarkdownで記載する。要求ごとに、導出元となるユースケース、フロー、ステップID、導出理由、および導出根拠として使用した図表の名称を記録する。図表を使用していない場合は「なし」と明記する。
6. **要求分析**：明確性、一貫性、検証可能性、実現可能性、依存関係、外部への影響を確認し、必要に応じて分類と優先順位を設定する。
7. **網羅性確認**：利害関係者要求、ユースケース、シナリオ、システム要求の対応、内容、導出根拠を確認する。
8. **レビュー・合意**：正確性、完全性、妥当性をレビューし、必要に応じて利害関係者要求へフィードバックしてから確定する。

分析結果は `docs/requirements/systems/<system>/システム要求分析.md` に保存すること。分析文書と `.sdoc` は、UID、要求文、親要求、検証方法、導出関係を一致させること。

### 文書配置と識別子

- 利害関係者ニーズは `docs/requirements/stakeholder/stakeholder_needs.sdoc`、利害関係者要求は同ディレクトリの `stakeholder_requirements.sdoc` に配置する。
- システム要求とソフトウェア要求は、対象システムごとに `docs/requirements/systems/<system>/` へ配置し、要求レベル別の文書に分ける。
- 所属先は文書とディレクトリ構成を正とし、`TAGS` だけに依存しない。
- 各文書のDocument UIDと各Requirement UIDはリポジトリ内で一意とする。
- 新規Requirement UIDは所属システムを識別できる命名規則に従う。既存UIDは規則への適合だけを目的に変更しない。
- 共通の利害関係者ニーズと要求は下位要求から追跡可能にする。
- システムをまたぐ責務はインターフェース要求として明示し、責務の境界を記載する。
- ソフトウェア要求の親は、同じ対象システムのシステム要求とする。

### 変更と検証

コードの動作、外部仕様、機能を追加、変更または削除する場合は、対応する要求仕様の更新または廃止が必要か確認すること。要求の意味を推測で変更せず、既存のトレーサビリティを維持すること。

`.sdoc` を変更した場合は次を実行すること。

```bash
strictdoc export docs --output-dir build/strictdoc
```

エクスポートに加え、次をレビューまたは検査スクリプトで確認すること。

- 要求レベルタグが1つだけ設定されている
- `Parent` の要求レベルと参照先が正しい
- 利害関係者要求、システム要求、ソフトウェア要求が孤立していない
- 利害関係者ニーズに検証方法が設定されていない
- 利害関係者要求、システム要求、ソフトウェア要求の `COMMENT` が検証方法の規約に従っている
